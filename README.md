## What This Solves

People who have used the same Gmail account for a decade accumulate tens of
thousands of emails. They know it's a mess. They feel vaguely bad about it. But
there's no practical way to fix it — Gmail's own tools require going through
emails one at a time or writing search queries.

Existing tools (Clean Email, Unroll.me, SaneBox) solve this by asking for full
mailbox access and reading everything. That's a hard sell — you're handing over
your entire correspondence to a third party.

Sweepyr's answer: **classify emails using only metadata.** Sender address,
subject line, and headers are enough to correctly sort ~99% of emails. The Gmail
API's `format=metadata` parameter makes it impossible for body content to reach
our servers — it's a technical guarantee, not a policy promise.

The user connects Gmail, clicks one button, and gets their inbox sorted into 14
categories with a suggested action for each. They review and bulk-archive,
label, or trash. Nothing happens without their explicit confirmation.

Built for the Indian market — the rule engine knows HDFC, SBI, Paytm, PhonePe,
Swiggy, Zomato, Naukri, IRCTC, CRED, Flipkart, MakeMyTrip and ~200 other Indian
senders, which is where the accuracy advantage over global tools comes from.

## Setup From Scratch

### Prerequisites

- **Node.js ≥ 20.9.0** — Next.js 15 requires it. Check with `node --version`.
  If you're on 18, use `nvm install 20 && nvm use 20`.
- A Google account
- A MongoDB Atlas account (free tier is fine)

### 1. Clone and install

```bash
git clone <your-repo-url> sweepyr
cd sweepyr
npm install
```

### 2. Google Cloud Console setup

1. Go to [console.cloud.google.com](https://console.cloud.google.com), create a
   new project called `sweepyr`.
2. **APIs & Services → Library** → search "Gmail API" → **Enable**.
3. **APIs & Services → OAuth consent screen** → choose **External** → fill in app
   name, support email, developer email → Save through the remaining steps →
   leave it in **Testing** mode.
4. Still on the consent screen, scroll to **Test users** → **Add Users** → add
   your own Gmail address. Without this you'll get `Error 403: access_denied`.
5. **APIs & Services → Credentials** → **Create Credentials → OAuth 2.0 Client
   ID** → Application type **Web application**.
   - Authorised JavaScript origins: `http://localhost:3000`
   - Authorised redirect URIs: `http://localhost:3000/api/auth/callback/google`
6. Copy the **Client ID** and **Client Secret**.

### 3. MongoDB Atlas setup

1. Create a cluster (free M0 tier).
2. **Database Access** → Add New Database User → username + **autogenerated
   password** (avoid special characters, they need URL-encoding in the URI).
3. **Network Access** → Add IP Address → **Allow Access from Anywhere**
   (`0.0.0.0/0`).
4. **Connect → Drivers** → copy the connection string. Insert the database name
   between the `/` and the `?`:
   ```
   mongodb+srv://user:pass@cluster.xxxxx.mongodb.net/sweepyr?retryWrites=true&w=majority
   ```

### 4. Gemini API key

1. Go to [aistudio.google.com](https://aistudio.google.com) → **Get API key** →
   **Create API key** → select your `sweepyr` project.
2. **Enable billing** on the Google Cloud project. The free tier quota is
   effectively zero for this workload and every AI call will fail silently.

### 5. Sentry (optional but recommended)

```bash
npx @sentry/wizard@latest -i nextjs
```
Creates a project, generates `instrumentation.ts`, `instrumentation-client.ts`,
`sentry.server.config.ts`, `sentry.edge.config.ts`, and wraps `next.config.mjs`.
Grab the DSN from **Settings → Client Keys (DSN)**.

### 6. Environment variables

Create `.env.local` in the project root (it's gitignored):

```
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
MONGODB_URI=
NEXTAUTH_URL=http://localhost:3000
NEXTAUTH_SECRET=
GEMINI_API_KEY=
SENTRY_DSN=
NEXT_PUBLIC_SENTRY_DSN=
```

Generate `NEXTAUTH_SECRET` with:
```bash
openssl rand -base64 32
```

### 7. Run

```bash
npm run dev
```

Open `http://localhost:3000`, click "Continue with Google", approve all three
Gmail permission checkboxes, and you should land on the dashboard.

## Dependencies and Why Each Exists

| Package | What job it does here |
|---|---|
| **next** | The framework. App Router gives us file-based routing, server components (so `getServerSession` runs server-side without exposing tokens), and API routes — meaning no separate Express server. |
| **react** / **react-dom** | UI. Function components and hooks only. |
| **next-auth** | Handles the entire Google OAuth dance — redirect, consent, callback, token exchange, session cookies. Without it we'd be hand-rolling OAuth. Its `callbacks` are where we hook in to persist the refresh token to MongoDB. |
| **mongoose** | MongoDB ODM. Gives us schemas (so `Email` documents have a guaranteed shape), the compound unique index that prevents duplicate emails per user, and `findOneAndUpdate` with `upsert` which makes re-scanning idempotent. |
| **googleapis** | Google's official Node client. We use `google.auth.OAuth2` to build a credentialed client from a refresh token, and `google.gmail({version:'v1'})` for all mailbox operations. It transparently refreshes expired access tokens for us. |
| **@google/generative-ai** | Gemini client for the AI classification layer. Only called for emails the rule engine can't resolve. |
| **@sentry/nextjs** | Error tracking. Without it, production failures are invisible. The context objects we attach (`route`, `userId`, `action`) are what make a stack trace actionable. |
| **tailwindcss** | Present and partially used, but see the styling note below. Most UI is inline styles. |

### A note on Tailwind

Tailwind is installed and some older components still use it, but **inline styles
are the convention in this codebase**. Tailwind repeatedly failed to render
correctly here — grids collapsing, `fixed` positioning breaking, z-index being
overridden, colours not applying. Every occurrence was resolved by switching to
inline `style={{}}`. If you're writing new UI, use inline styles. If you touch an
existing component and something looks wrong, convert it rather than debugging
Tailwind.

## Code Walkthrough

### Models

#### `models/User.js`

One document per user. The schema:

```js
{
  googleId: String (unique),   // Google's subject ID — our primary lookup key
  email: String (unique),
  name: String,
  image: String,               // Google profile picture URL
  refreshToken: String,        // ← the critical field
  tier: String,                // 'free' | 'pro' | 'annual' | 'deepclean'
  usage: {
    cleanupCount: Number,
    monitorCount: Number,
    resetAt: Date,
  },
  timestamps: true,
}
```

`refreshToken` is what lets the server call Gmail on the user's behalf when they
aren't actively present — background jobs, queued processing. Every Gmail API
call in the app starts by loading this field.

#### `models/Email.js`

One document per email per user. **There is no `body` field and there never
should be.**

```js
{
  userId: ObjectId (ref User, indexed),
  messageId: String,           // Gmail's ID — used for all write-back calls
  threadId: String,
  from: String,                // raw header, e.g. 'Amazon <no-reply@amazon.in>'
  subject: String,
  date: String,                // raw Date header
  labelIds: [String],          // Gmail's own labels, e.g. ['INBOX','UNREAD']
  snippet: String,             // Gmail's short preview — NOT the body
  headers: Mixed,              // lowercased key→value map of fetched headers
  hasAttachment: Boolean,

  category: String,            // null once actioned
  confidence: Number,
  classificationSource: String,// 'rules' | 'domain' | 'ai' | 'user'
  isProcessed: Boolean,
  actionTaken: String,         // 'archive' | 'trash' | 'label' | null

  source: String,              // 'scanned' | 'monitored'  (for Phase 6)
  monitoredAt: Date,           // (for Phase 6)
}
```

Compound unique index on `{ userId, messageId }` — prevents duplicates and makes
per-user queries fast even across millions of documents.

#### `models/ActionHistory.js`

Audit trail. One document per action.

```js
{
  userId: ObjectId,
  action: String,              // 'archive' | 'trash' | 'label'
  category: String,
  emailCount: Number,
  labelName: String,           // only for label actions
  messageIds: [String],        // ← makes a future "undo" feature possible
  timestamps: true,
}
```

Serves three purposes: debugging when a user reports something, analytics on
which actions get used, and the raw material for an undo feature later.

### lib/ — Core Logic

#### `lib/mongoose.js`

Exports a single default `connectDB()`.

The important thing here is the **global connection cache**. Next.js hot-reloads
the server on every file save in dev. Without caching, each reload would open a
new MongoDB connection and you'd exhaust Atlas's connection limit within minutes.

```js
let cached = global.mongoose
if (!cached) cached = global.mongoose = { conn: null, promise: null }
```

`connectDB()` returns the cached connection if it exists, otherwise creates one
and caches the *promise* (not just the result) so concurrent calls during startup
don't each open a connection.

It also has diagnostic error branches — `MongoNetworkError` prints a hint about
the IP whitelist, `MongoParseError` about URI format, `code === 8000` about wrong
credentials. These were added after a debugging session where the real problem
(wrong DB user) was masked by a generic `AccessDenied` error at the OAuth layer.

**Called from:** every API route, before any database work.

#### `lib/authOptions.js`

Exports `authOptions` — the NextAuth configuration object. Kept in its own file
rather than inline in the route handler because `getServerSession(authOptions)`
needs to import it from server components too.

**Provider config.** Three things matter:
- `access_type: 'offline'` — tells Google to issue a refresh token
- `prompt: 'consent'` — forces the consent screen even on repeat sign-ins, which
  guarantees a fresh refresh token
- `scope` — `openid email profile` plus `gmail.readonly`, `gmail.labels`,
  `gmail.modify`

**`signIn` callback.** Runs immediately after Google returns the user. Upserts
the User document. The subtle bit:

```js
if (account.refresh_token) {
  existingUser.refreshToken = account.refresh_token
  await existingUser.save()
}
```

The `if` guard matters — Google only sends a refresh token on first consent or
forced re-consent. On a normal repeat sign-in `account.refresh_token` is
`undefined`, and overwriting unconditionally would wipe a working token.

Returns `true` to allow sign-in, `false` to reject. **If this returns `false`,
NextAuth shows a generic "Access Denied" page with no explanation** — which is
why there's error logging inside it.

**`jwt` callback.** Fires whenever a JWT is created or refreshed. Loads the
user's `tier` from MongoDB and attaches it to the token.

**`session` callback.** Copies `token.sub` → `session.user.id` and
`token.tier` → `session.user.tier`, making both available via `useSession()` on
the client and `getServerSession()` on the server. Also calls
`setUserContext()` so Sentry knows which user hit an error.

#### `lib/gmail.js`

All **read** operations against Gmail, plus auth-error detection.

**`getGmailClient(refreshToken)` → Gmail API client**
Builds an `OAuth2` client from the app's client ID/secret, sets the user's
refresh token as credentials, and returns `google.gmail({version:'v1', auth})`.
The googleapis library handles exchanging the refresh token for a short-lived
access token automatically on each call.

**`isAuthError(error)` → boolean**
Pattern-matches the error message for `invalid_grant`, `token has been expired`,
`token has been revoked`, `invalid_rapt`, or a 401 status.

**`gmailCall(fn)` → result of fn**
Wraps any Gmail API call. If `isAuthError` matches, it throws a new error with
`code === 'GMAIL_AUTH_EXPIRED'`. Everything else rethrows unchanged. This is the
single place auth failures are normalised, so API routes only need one check.

**`getEmailCount(refreshToken)` → Number**
Calls `users.getProfile()` and returns `messagesTotal`.
*Note:* this counts everything including Trash and Spam, so it doesn't decrease
after archiving. An attempt to use `messages.list().resultSizeEstimate` for an
inbox-only count returned 0 and was reverted.

**`getMessageIds(refreshToken, maxResults, pageToken)` → `{ messageIds, nextPageToken }`**
Calls `messages.list` filtered to `labelIds: ['INBOX']`. Gmail caps
`maxResults` at 500 per request. Returns message IDs only — no content.

**`getEmailMetadata(refreshToken, messageId)` → email object**
The privacy-critical function. Calls `messages.get` with:

```js
format: 'metadata',
metadataHeaders: ['From','Subject','Date','List-Unsubscribe',
                  'Precedence','X-Mailer','Reply-To','Content-Type','To']
```

`format: 'metadata'` is what makes body access impossible — Google's API simply
does not include the body in the response. Headers come back as an array of
`{name, value}` objects, which this function flattens into a lowercased key→value
map for easier lookup downstream.

**`detectAttachment(payload)` → boolean** (module-private helper)
Walks the payload parts recursively looking for a non-empty `filename` or an
attachment-ish `mimeType` (`application/pdf`, `application/octet-stream`,
`application/vnd.*`), or a top-level `multipart/mixed` content type. Reads
metadata about parts only — never their content.

**`getBatchEmailMetadata(refreshToken, messageIds)` → array**
Fires all `getEmailMetadata` calls in parallel via `Promise.allSettled` and
returns only the fulfilled results. `allSettled` rather than `all` so one failed
email doesn't abort the whole batch.

#### `lib/gmailActions.js`

All **write** operations. Every function chunks its input because Gmail has
per-request limits.

**`getOrCreateLabel(refreshToken, labelName)` → labelId**
Calls `labels.list`, looks for an exact name match, returns its ID. If absent,
calls `labels.create` with `labelListVisibility: 'labelShow'` and returns the new
ID. Idempotent — safe to call repeatedly.

**`archiveEmails(refreshToken, messageIds)` → count**
`messages.batchModify` with `removeLabelIds: ['INBOX']`. Chunks of 1000 (Gmail's
batch limit). Archived mail stays in All Mail and is fully searchable — nothing
is lost.

**`trashEmails(refreshToken, messageIds)` → count**
Gmail has **no batch endpoint for trash**, so this calls `messages.trash`
individually in chunks of 50 via `Promise.allSettled`, with a 500ms pause between
chunks to stay under rate limits. Counts only fulfilled results.

**`messages.delete` is deliberately never called anywhere in this codebase.**
Trashed mail is recoverable for 30 days, which means no bug here can permanently
destroy a user's email.

**`applyLabel(refreshToken, messageIds, labelId)` → count**
`messages.batchModify` with `addLabelIds: [labelId]`. Chunks of 1000.

**`chunkArray(array, size)`** — module-private splitter.

#### `lib/logger.js`

Thin wrapper over Sentry so error handling is consistent and console noise is
dev-only.

- **`logError(error, context)`** — always `console.error`; in production also
  sends to Sentry with each context key attached via `scope.setExtra()`. The
  context object is the whole point — "invalid_grant" alone is useless,
  "invalid_grant in /api/gmail/count for user abc123" is actionable.
- **`logWarning(message, context)`** — same, at warning level.
- **`logInfo(message, context)`** — console only, never sent to Sentry.
- **`setUserContext(user)`** — attaches user id/email to Sentry's scope.
- **`clearUserContext()`** — clears it on sign out.

#### `lib/apiHelpers.js`

`authExpiredResponse()`, `unauthorizedResponse()`, and a `withErrorHandling()`
route wrapper. Standardises the shape of error responses.

#### `lib/tierLimits.js`

Single source of truth for monthly cleanup limits and the usage reset, used by
both `/api/gmail/process` (enforcement + metering) and `/api/user/status`
(read-only display) so the two can never disagree.

**`TIER_LIMITS`** — `{ free: 100, pro: 500, annual: 10000, deepclean: 5000 }`.
Annual is a credit pool per the pricing page ("10,000 cleanup credits/year"),
not a monthly allocation — the number is the same either way since there's no
monthly-reset distinction implemented for it yet.

**`getCleanupLimit(tier)`** — `TIER_LIMITS[tier]`, falling back to the free
limit for an unrecognised tier.

**`ensureFreshUsage(user)`** — the reset mechanism. Checks
`user.usage.resetAt`; if more than 30 days have passed, zeroes
`usage.cleanupCount`, sets `resetAt` to now, and saves. This is a **lazy
30-day rolling reset**, not a calendar-month cron — there's no scheduler
running yet, so the reset happens on whichever request notices it's overdue.
Both `/api/gmail/process` and `/api/user/status` call this before reading
`usage`, so a user always sees consistent numbers regardless of which route
they hit first after the window expires.

### lib/classifier/ — The Classification Pipeline

This is the heart of the product.

#### `lib/classifier/index.js`

**`classifyEmail(email)` → `{ category, confidence, reason, classificationSource }`**

Runs three layers in order, returning as soon as one produces a result at or
above `CONFIDENCE_THRESHOLD` (0.85):

```js
rules → if confidence >= 0.85, return
domain → if confidence >= 0.85, return
ai → always returns something (falls back to 'Uncertain' on failure)
```

**`classifyEmails(emails)` → array of results**
Sequential loop with a delay after any email that hit the AI layer. Largely
superseded by the parallel batching inside `/api/gmail/process`, but still used
by the legacy `/api/gmail/classify` route.

#### `lib/classifier/rules.js`

Layer 1. Pure JavaScript, zero cost, instant. Handles ~99% of emails in practice.

**`KNOWN_DOMAINS`** — a ~230-entry map of sender domain → `{ category, confidence }`,
organised by sector. **Bank/NBFC/insurance/credit-card/BNPL and stock-broker
domains are deliberately NOT here** — see "Attachment-sensitive domains" below
for why.

- UPI/wallets — paytm.com, phonepe.com, razorpay.com, mobikwik.com, amazonpay.in
- Insurance marketplaces (aggregators, left flat) — policybazaar.com, acko.com
- Job portals — naukri.com, indeed.com, internshala.com, hirist.com, instahyre.com,
  cutshort.io, foundit.in, linkedin.com
- E-commerce — flipkart.com, amazon.in, myntra.com, ajio.com, meesho.com,
  bigbasket.com, blinkit.com, zepto.in
- Food — swiggy.in, zomato.com
- Travel — makemytrip.com, irctc.co.in, goibibo.com, indigo/goindigo.in,
  spicejet, cleartrip, yatra, ixigo, oyo, redbus, booking.com, airbnb
- Utilities — jio.com, airtel.in, bsnl, bescom, tatapower
- Government / Tax — incometax.gov.in, epfindia.gov.in, uidai.gov.in, digilocker.gov.in
- Ed-tech (course-selling) — byjus, unacademy, coursera, udemy, upgrad, scaler,
  pw.live, vedantu.com, testbook.com
- Coding practice (Notifications, not Promotions — contest reminders, not

- Global ESPs — substack, mailchimp, sendgrid, klaviyo, amazonses
- Social — twitter/x, facebook, instagram, youtube, quora, reddit, medium
- Dating (Social) — tinder.com, bumble.com, hinge.co, trulymadly.com, aisle.co,

- Healthcare — pharmacy (Receipts, like e-commerce) — 1mg.com, pharmeasy.in,
  netmeds.com, medlife.com
- Real estate (Promotions) — nobroker.in, magicbricks.com, 99acres.com, housing.com
- Wedding vendors (Promotions) — wedmegood.com, weddingwire.in
- Gaming / fantasy sports (Promotions) — dream11.com, mpl.live, winzogames.com

- Religious / spiritual (Newsletter) — isha.sadhguru.org, artofliving.org
- Dev tools — github.com, mongodb.com, onedrive.com

**Attachment-sensitive domains** — three separate arrays (`BANK_ATTACHMENT_DOMAINS`,
`BROKER_ATTACHMENT_DOMAINS`, `HEALTHCARE_ATTACHMENT_DOMAINS`), checked instead of
a flat `KNOWN_DOMAINS` entry. Each has a low-stakes default (no attachment) and
escalates to a different, vertical-specific category when `hasAttachment` is
true — **not all attachments escalate to the same place**:

| Domains | No attachment → | With attachment → |
|---|---|---|
| Banks/NBFCs/insurance/credit cards/BNPL (hdfcbank.com, icicibank.com, sbi.co.in, cred.club, sbicard.com, hdfclife.com, licindia.in, …) | `Notifications` — likely an alert or marketing | `Finance` @ 0.97 — likely a statement or policy document |
| Stock brokers (zerodha.com, groww.in, upstox.com, angelone.in, 5paisa.com) | `Newsletter` — likely market commentary or a portfolio ping | `Finance` @ 0.97 — likely a contract note or tax/P&L statement |
| Healthcare diagnostics (practo.com, apollo247.com) | `Notifications` — likely an appointment reminder | `Personal` @ 0.95 — likely a lab report or prescription (a personal record, not a financial one, hence `Personal` not `Finance`) |

**Subject pattern matchers** — each returns a boolean:
- `isOTPEmail` — `\botp\b`, "verification code", "one time password",
  `\d{4,8} is your`, "security code"
- `isBankPromotional` — "apply now", "YONO", "need a loan", "discover more",
  "pre-approved", "exclusive offer", "personal loan", "credit card"
- `isTravelPromotional` — "% off", "flash sale", "book now and save", "limited
  time/seats", "deal of the day" — catches marketing from travel domains before
  their flat `Travel` default claims it (not domain-restricted, so it can also
  catch discount language from any sender)
- `isTransactionEmail` — "debited", "credited", "UPI", "NEFT/RTGS/IMPS",
  "a/c ... debited", "payment due", "statement ready", plus broker trade-execution
  phrasing ("buy/sell order ... executed", "shares bought/sold", "trade confirmation")
- `isReceiptEmail` — "your order", "^shipped:", "^ordered:", "out for delivery",
  "invoice", "your return of"
- `isTravelEmail` — "flight", "boarding pass", "PNR", "itinerary", "e-ticket"
- `isJobEmail` — "job alert", "N new jobs", "jobs matching", "recommended jobs"
- `isWorkEmail` — "urgent requirement", "hiring for", "interview scheduled",
  "your CV/resume"
- `isFinanceEmail` — "account summary", "auto debit", "expense ratio",
  "policy no.", "mutual fund", "portfolio", "closing bell"

**`classifyByRules(email)`** — single priority chain, the order is the important part:

```
1.  OTP subject patterns                          → OTP & Security      0.97
2.  Bank/travel-promotional subject patterns       → Promotions          0.88   ← before any domain default
3.  Attachment-based escalation (bank/broker/       → Finance 0.97 /
    healthcare domains, or generic finance subject)   Personal 0.95        ← before transaction/receipt patterns
4.  Transaction subject patterns                   → Transactions        0.93
5.  Receipt subject patterns                       → Receipts            0.88   ← before the flat domain lookup
6.  KNOWN_DOMAINS lookup                            → mapped category     0.85–0.98
7.  No-attachment defaults for attachment-sensitive → Notifications/Newsletter 0.85
    domains (bank/broker/healthcare)
8.  List-Unsubscribe + Precedence: bulk             → Newsletter          0.90
8.5 List-Unsubscribe alone                          → Promotions          0.82
9.  Finance subject patterns                        → Finance             0.88
10. Travel subject patterns                         → Travel              0.88
11. Job alert patterns                              → Jobs & Careers      0.85
12. Recruiter patterns                               → Jobs & Careers      0.87
13. Precedence: bulk alone                           → Promotions          0.85
    otherwise                                        → null (fall through)
```

**Why bank/travel-promotional sits above the domain lookup:** `sbi.co.in` maps to
Finance, but SBI also sends YONO app adverts and loan offers; `makemytrip.com`
maps to Travel, but also sends "Flat 40% off flights" marketing. If the domain
lookup ran first it would swallow both into their "important" category. Checking
subject intent first lets promotional emails escape before the domain claims
them. The general principle: **a sender's identity doesn't determine an email's
purpose.**

**Why receipt patterns also sit above the domain lookup:** the mirror-image bug.
`myntra.com` maps flatly to `Promotions`, so a genuine "Your order has been
shipped" email used to get stuck as Promotions too — the domain lookup returned
before `isReceiptEmail()` ever ran. Moving the receipt check earlier fixes this
for every Promotions-mapped e-commerce/marketing domain at once, the same way
`isBankPromotional` already fixed it for banks.

**Why attachment-based escalation runs before transaction/receipt patterns, not
after:** it used to run after, and it was effectively dead code for banks — every
bank domain already had a flat `KNOWN_DOMAINS` entry that returned before the
attachment check was ever reached, so attachment presence made zero difference
despite the code and comments suggesting otherwise. Fixing this required two
things: pulling the attachment-sensitive domains **out** of `KNOWN_DOMAINS`
entirely (so the flat lookup can't shadow them), and moving the escalation check
early enough that it isn't itself shadowed by `isTransactionEmail`'s
`/your.*statement/i` pattern (a bank statement PDF was matching that as
"Transactions" before it ever reached the Finance escalation).

**Why attachment escalates to different categories per vertical:** an attachment
is not a generic "this is important" flag — it's a signal about *what kind of
document this is*. A bank/broker attachment is a financial document (→ `Finance`).
A healthcare-diagnostics attachment is a personal medical record, not a money
document (→ `Personal`). A travel attachment (e-ticket, itinerary) doesn't change
the category at all — `Travel` was already the correct destination either way,
so only the promotional-override matters there, not an escalation.

#### `lib/classifier/domain.js`

Layer 2. Runs only when rules return `null` or low confidence.

**`classifyByDomain(email)`**
- If the sender domain is a personal provider (gmail.com, yahoo.com, outlook.com,
  icloud.com, rediffmail.com…) → **returns `null` deliberately**, pushing it to
  the AI layer. Only AI can judge whether a personal email is Work, Personal, or
  something else.
- If the domain matches bulk-sender subdomain patterns (`^mail\.`, `^em\d+\.`,
  `^news\.`, `^noreply\.`, `^bounce\.`, `^bulk\.`) → Promotions at 0.78
- If the local part contains `noreply`/`no-reply` → Notifications at 0.80
- Otherwise `null`

`extractBaseDomain()` strips subdomains — `em123.newsletter.amazon.com` →
`amazon.com` — so subdomain variants resolve to the same brand.

#### `lib/classifier/ai.js`

Layer 3. The only part that costs money.

**`VALID_CATEGORIES`** — the 14 allowed strings. Anything Gemini returns outside
this list becomes `Uncertain`.

**`classifyByAI(email, retryCount = 0)`**

The prompt sends **only**:
```
Sender: {from}
Subject: {subject}
Has unsubscribe option: {yes/no}
Precedence header: {value}
```

Plus the category list with one-line descriptions. It explicitly asks for JSON
only, no preamble, no markdown.

Response handling:
1. `text.replace(/```json|```/g, '').trim()` — strip markdown fences, which
   Gemini adds despite being told not to
2. `JSON.parse`
3. Validate the category against `VALID_CATEGORIES`
4. Return `{ category, confidence, reason }`

**Retry logic:** on a 429, waits `(retryCount + 1) * 5000` ms — 5s, 10s, 15s —
and recurses up to 3 times. This was added because without it a brief rate limit
would mark dozens of emails as `Uncertain`.

**The silent-failure trap:** the catch-all returns
`{ category: 'Uncertain', confidence: 0 }`. A dead API key, an expired billing
account, or a deprecated model name all look identical to "the AI wasn't sure."
**Whenever classification quality drops, check the terminal for 404s or 429s
before assuming a logic bug.** This has happened four separate times with model
deprecations.

### app/api/ — Route Handlers

#### `app/api/auth/[...nextauth]/route.js`
Three lines. Instantiates NextAuth with `authOptions` and exports the handler as
both `GET` and `POST`. The `[...nextauth]` catch-all folder captures `/signin`,
`/signout`, `/session`, `/callback/google`, etc.

#### `app/api/gmail/count/route.js` — `GET`
Session guard → load user → `getEmailCount(refreshToken)` → `{ count }`.

#### `app/api/gmail/process/route.js` — `GET` (SSE) — **the main pipeline**

The most complex route. Streams progress while scanning and classifying.

```js
const stream = new ReadableStream({ start(c) { controller = c } })

function send(data) {
  controller.enqueue(encoder.encode(`data: ${JSON.stringify(data)}\n\n`))
}

;(async () => { /* all the work */ })()   // detached, not awaited

return new Response(stream, {
  headers: {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
  }
})
```

**Why the detached IIFE:** the `Response` must be returned *immediately* so the
browser receives the SSE headers and opens the connection. If you `await` the
processing first, nothing streams — the client just waits for a single response.

**The `data: {...}\n\n` format** is the entire SSE protocol. Two newlines
terminate an event.

Flow:
1. `ensureFreshUsage(user)` (see `lib/tierLimits.js`), then compute
   `remaining = cleanupLimit - usage.cleanupCount`. If `remaining <= 0`, send
   a `USAGE_LIMIT_REACHED` error event and close the stream — no scan happens.
   Otherwise read `batchSize` from the query string and clamp it to
   `min(requestedSize, remaining)` server-side (never trust the client)
2. `getMessageIds()` for the batch
3. Loop in chunks of 50: fetch metadata in parallel, upsert into MongoDB, send a
   `stage: 'scanning'` event
3.5. `user.usage.cleanupCount += emails.length; await user.save()` — meters
   usage against the count actually fetched this request, not the requested
   batch size. Happens once, right after scanning finishes and before
   classification starts.
4. Query unprocessed emails from MongoDB
5. Loop in batches of 5: `Promise.allSettled(batch.map(classifyEmail))`, write
   results back, 300ms pause, send a `stage: 'classifying'` event
6. Send `stage: 'done'` with `summary`, `layerStats`, `classified`
7. `controller.close()` in a `finally`

**Building the summary as it goes:**
```js
summary[category] = (summary[category] || 0) + 1
```
Starts as `{}` and accumulates — `{ Newsletter: 45, Promotions: 23, ... }`. This
is exactly the shape the dashboard renders.

**Rate limiting:** 5 concurrent AI calls with 300ms between batches ≈ 16 calls
per second, comfortably within Gemini's paid limits. Sequential with 1s delays
would take ~12 minutes for 5,000 emails; this takes ~3–4.

#### `app/api/gmail/scan/route.js` and `classify/route.js` — dead code
Superseded by `/process`. Both files are now **entirely commented out** (not
deleted) — the frontend functions that called them (`startScan()`,
`startClassification()` in `CategorySummary.js`, also commented out) were never
wired to any button. Left in place rather than deleted so the reasoning is
visible in-repo; still count as routes against Vercel's function limit since
Next.js registers the route segment regardless of whether it exports a handler.

#### `app/api/emails/route.js` — `GET`
Paginated emails for a category. Query params `category` and `page`, 20 per page.
Returns `{ emails, total, page, totalPages, hasMore }`.

The `.select()` list matters — `headers` **must** be included or the unsubscribe
button will never appear (this was a real bug: headers were stored correctly but
not returned, so `getUnsubscribeUrl` always got `undefined`).

#### `app/api/emails/[messageId]/route.js` — `PATCH`
Reclassify a single email. Sets `category` and `classificationSource: 'user'`.

Two things to note:
- `const { messageId } = await params` — **`params` is a Promise in Next.js 15**
- The query filters on `{ messageId, userId: user._id }` — the `userId` clause is
  a security check preventing a user from modifying another user's emails by
  guessing a message ID

**This route only touches MongoDB. It never calls Gmail.** Reclassifying is a
sorting correction, not a mailbox operation.

#### `app/api/emails/summary/route.js` — `GET`
MongoDB aggregation producing category counts:

```js
Email.aggregate([
  { $match: { userId, isProcessed: true, category: { $ne: null } } },
  { $group: { _id: '$category', count: { $sum: 1 } } },
])
```

Converts `[{_id:'Finance', count:15}]` into `{ Finance: 15 }`. A second
aggregation does the same for `classificationSource`. This is what makes the
dashboard survive a page reload without rescanning.

#### `app/api/emails/actions/route.js` — `POST`
Bulk action on an entire category. Body: `{ action, category }`.

Loads all messageIds for that user+category, dispatches to
`archiveEmails`/`trashEmails`/`applyLabel`, writes an `ActionHistory` record,
then:

```js
await Email.updateMany(
  { userId, category },
  { $set: { actionTaken: action, category: null, isProcessed: false } }
)
```

**Setting `category: null` is what removes emails from the category view.**
Without it they'd reappear after acting on them.

#### `app/api/emails/group-action/route.js` — `POST`
Same as above but takes an explicit `messageIds` array instead of a category —
used for per-sender-group actions. Accepts `archive`, `trash`, and `label`.

#### `app/api/emails/feed-action/route.js` — `POST`
Single-email action from the monitoring feed. No confirmation modal on the client
side for these — one email in a live feed doesn't warrant the friction.

#### `app/api/emails/monitored/route.js` — `GET`
Queries emails with `source: 'monitored'`. Returns empty until Phase 6 populates
that field. Caps the feed at 50 (`MAX_FEED`) with 10 per page, and returns
`hiddenCount` for anything beyond.

#### `app/api/stats/route.js` — `GET`
Aggregates `ActionHistory` by action type to produce
`{ trashed, archived, labelled, totalCleaned, totalSorted }`.

#### `app/api/version/route.js` — `GET`
Public, no session guard — the point is to be `curl`-able without signing in.
Returns `{ version, commitSha, branch, environment, commitMessage }` sourced
from Vercel's auto-injected git env vars (`VERCEL_GIT_COMMIT_SHA`,
`VERCEL_GIT_COMMIT_REF`, `VERCEL_ENV`). Fastest way to confirm what's actually
live on a given environment without opening the Vercel dashboard. The same
values are also re-exposed client-side as `NEXT_PUBLIC_*` vars (see
`next.config.mjs`) and logged to the browser console on load
(`app/Providers.js`) and the server console at cold start (`instrumentation.ts`).

#### `app/api/user/status/route.js` — `GET`
Counts processed emails for the user. `isNewUser: processedCount === 0` drives
whether the onboarding card renders. Also calls `ensureFreshUsage()` and
returns `tier` and `usage: { used, limit, remaining }` — this is how the
frontend (`DashboardClient` → `CategorySummary`) learns the user's real tier
and quota, rather than a hardcoded value.

#### `app/dashboard/DashboardClient.js` — client root

#### `app/dashboard/CategorySummary.js`

Two sections: the mailbox card and the inbox report.

**Mailbox card** — privacy note, email count, batch size selector, and the

## Non-Obvious Logic Explained

**Why `format: 'metadata'` and not just "don't read the body"**
It's a Google-side constraint. The API response literally does not contain the
body when this parameter is set. Even a bug or a malicious code change couldn't
access it without also changing this parameter. That's the difference between a
technical guarantee and a policy promise, and it's the entire product positioning.

**Why the `if (account.refresh_token)` guard in signIn**
Google issues a refresh token on first consent and on forced re-consent only. On
ordinary repeat sign-ins the field is `undefined`. Assigning unconditionally
would overwrite a working token with `undefined` and break all background access.

**Why `Promise.allSettled` everywhere instead of `Promise.all`**
`all` rejects the whole batch if any single promise rejects. When fetching 50
emails, one deleted or inaccessible message would lose the other 49. `allSettled`
returns every outcome and we filter for `status === 'fulfilled'`.

**Why the SSE route returns before doing the work**
The `Response` object carries the SSE headers. Until the browser receives them,
`EventSource` hasn't opened a stream and nothing can be pushed to it. So the work
runs in a detached async IIFE writing to the stream controller, while the
`Response` returns immediately.

**Why `category: null` after an action**
All category views query `Email.find({ userId, category })`. Setting it to null
removes the email from every category at once, without deleting the record —
which we keep for `ActionHistory` reconciliation and future undo.

**Why the AI layer returns `Uncertain` instead of throwing**
A single failed classification shouldn't abort a 500-email run. But the cost is
that infrastructure failures are indistinguishable from genuine uncertainty in
the UI. This bit hard four times with model deprecations. Always check logs.

**Why personal email domains return `null` from the domain layer**
`gmail.com` tells you nothing about intent — it could be a friend, a recruiter, a
freelance client, or a scam. That ambiguity is exactly what the AI layer exists
for, so the domain layer deliberately declines to guess.

**Why the modal is a fragment sibling rather than nested**
`position: fixed` is supposed to position relative to the viewport, but a parent
with `transform`, `filter`, or certain Tailwind utilities creates a containing
block that overrides this. The modal rendered at the bottom of the page content.
Rendering it as a sibling of the content div, with inline styles, avoids every
ancestor that could interfere.

**Why buttons check `!scanning` in their render conditions**
Without it, action buttons remain clickable while an async operation is running,
letting the user fire overlapping requests.

**Why `StatsBar` takes a `refreshKey` prop**
React has no built-in "refetch this child" mechanism. Putting an incrementing
number in the child's `useEffect` dependency array is the idiomatic workaround:
the parent bumps the number, React sees a changed dependency, the effect reruns.

**Why the progress bar measures against scanned emails, not the mailbox**
For a user with 63,295 emails, cleaning 17 is 0.03% — it rounds to 0.0% and the
bar renders empty, which looks broken. Measuring against the 181 emails actually
scanned gives 9.4%, which is both a more honest measure of the work they've done
and visibly encouraging.

**Why the bank-promotional check runs before the domain lookup**
Order-of-operations bug found in testing. `sbi.co.in` → Finance is correct for
statements and alerts, but SBI also sends YONO app adverts. Checking subject
intent first lets promotional emails escape before the domain claims them. The
general lesson: a sender's identity doesn't determine an email's purpose.

**Why "Reclassify" is not called "Move to"**
"Move to Spam" reads like it moves the email to Gmail's Spam folder. It doesn't —
it only changes the `category` field in MongoDB. The Gmail action happens
separately via Label/Archive/Trash. The wording was changed to remove that
ambiguity, including the source badge ("You sorted" not "You moved") and a
one-line hint under the category header restating it explicitly.
